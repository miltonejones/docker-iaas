## Summary

### Diagnosis

The `ERR_SSL_PROTOCOL_ERROR` for custom gateway domains is caused by **three interconnected bugs**, all in how the console server manages Caddy configuration in Docker deployments:

**Bug 1 (PRIMARY) — Caddyfile filesystem isolation:** `appendCaddySite()` in `server/src/caddy.ts` writes domain blocks to a local Caddyfile inside the **console** container (`/app/Caddyfile`). But the **Caddy** container reads from a completely different file — the host-mounted `/etc/caddy/Caddyfile` (from `docker-compose.yml`). The two containers have no shared filesystem for this file, so Caddy **never sees** any custom domain configuration. The dashboard shows `certStatus: "active"` only because `verifyRouteDomain()` sets a DB flag unconditionally — it doesn't actually check whether Caddy has the domain configured.

**Bug 2 — Wrong upstream address:** The generated Caddy site block uses `reverse_proxy localhost:4300`. Since Caddy runs in its own container, `localhost` refers to the Caddy container's loopback, not the console container. The main Caddyfile entry for `dockyard-ai.com` correctly uses `console:4300` (the Docker Compose service name), but custom domain blocks used `localhost:4300`.

**Bug 3 — `caddy reload` runs in the wrong container:** `reloadCaddy()` calls `caddy reload` via `execFile` inside the **console** container. Caddy's CLI isn't installed there (not in the `Dockerfile`), so it always fails with `ENOENT` and silently resolves. Even if it were installed, `caddy reload` communicates via Caddy's admin API at `localhost:2019`, which is inside the Caddy container — unreachable cross-container.

**Result:** When a browser connects to `https://ai.ktunes.app:443`, Caddy has no site block for that hostname → no TLS certificate available → TLS handshake fails → `ERR_SSL_PROTOCOL_ERROR`.

### Changes Made

**`server/src/caddy.ts`** — the only file changed:

1. **Docker-aware upstream** (`appendCaddySite`): Detects Docker via `/.dockerenv` and uses `console:4300` (Docker service name) instead of `localhost:4300`, matching the main Caddyfile entry.

2. **Docker API-based reload** (`reloadCaddy`): Uses dockerode (already a dependency) to:
   - Read the base Caddyfile directly from inside the Caddy container via `docker exec cat /etc/caddy/Caddyfile` (cached)
   - Combine it with locally-tracked custom domain blocks
   - Push the merged config to `/data/Caddyfile` inside the Caddy container (the `caddy_data` named volume, which is writable)
   - Run `caddy reload --config /data/Caddyfile` inside the Caddy container

3. **Graceful fallback**: Errors from the Docker API are caught and logged, never thrown — the API endpoint still succeeds. Non-Docker dev environments continue using the local `caddy reload` CLI.
