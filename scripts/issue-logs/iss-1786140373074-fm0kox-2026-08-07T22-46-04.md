## Diagnosis

**Root cause: JWT expiry with no re-authentication mechanism.**

The consumer's `initAuthHeader()` is called exactly once at startup (line 1534 of the original). When it creates a JWT via the local-DB strategy (line 179), the token has a 24-hour expiry (`exp: now + 86400`). After 24 hours, every API poll returns HTTP 401, but `consumeOne()` only logs the status code and returns `false` — it never:

1. **Attempts re-authentication** — `authHeader` is never cleared, so `initAuthHeader()` is never called again. The consumer is permanently locked out.
2. **Updates the status file** — `writeStatus()` is only called on three paths: no-auth heartbeat, "no issues" idle heartbeat, and after processing an issue. The error paths (`catch` block for failed fetch, `!res.ok` guard) never touch the status file. After 2 days of silent 401 responses, `consumer-status.json` still shows `"idle"` with `lastPoll` frozen at the last successful poll.

The combination means:
- The consumer process is alive and looping (5-second poll interval)
- Every poll gets 401 → logs "API returned HTTP 401" → returns `false` → sleeps 5s → repeats
- The status file is stale (2+ days old) because error paths don't write it
- Health checks read from that stale file and report everything as healthy

## Changes Made

Three edits to `/app/scripts/issue-consumer.mjs`:

1. **No-auth path now attempts re-authentication** (line 1218): When `authHeader` is empty/falsy, `consumeOne()` now calls `await initAuthHeader()` on every poll before returning. Previously it just logged a heartbeat once per minute and waited.

2. **API error paths now handle 401/403 recovery and update the status file** (lines 1232-1253):
   - When the API fetch fails (network error), the status file is updated with `"api-error"` state at most once per minute.
   - When the API returns a non-OK status (especially 401 or 403), the consumer clears the stale `authHeader`, calls `initAuthHeader()` to obtain a fresh JWT, and updates the status file. This makes the consumer self-healing when its token expires.

3. **Proactive periodic re-authentication in the main loop** (lines 1531-1556): The loop now tracks `lastReauth` and re-authenticates every 6 hours (`REAUTH_INTERVAL_MS = 6 * 60 * 60_000`), well within the 24-hour JWT expiry window. This prevents the problem from occurring in the first place rather than just recovering from it.
